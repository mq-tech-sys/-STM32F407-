# OTA 远程升级方案

> 面向本仓库的 STM32F407ZE 智能门锁固件，基于现有 **巴法云 MQTT + ESP8266 AT 透传** 链路，
> 不增加任何硬件、不更换通信模块。

---

## 一、先给结论

**能做，而且这块板子的余量很宽裕。**

| 项目 | 实测值 | 对 OTA 的意义 |
|---|---|---|
| 芯片 | STM32F407ZE | 512 KB Flash，8 个扇区，支持按扇区擦写 |
| 当前固件 | RO 37.4 KB / ROM 37.75 KB | 只占 7%，双缓冲绰绰有余 |
| 当前 RAM | RW+ZI 80.9 KB / 128 KB | 还剩约 46 KB，加 OTA 缓冲不吃紧 |
| 通信 | ESP8266 AT 透传 + 自实现 MQTT | 已经是双向长连接，可直接当传输通道 |
| 现有升级方式 | ST-Link / 串口 ISP | 必须拆机或插线，这就是要解决的点 |

但有 **三条硬约束** 必须先说明白，否则做出来的东西会变成"升级一次砖一次"：

1. **必须新增一个 Bootloader**，并且第一次要用 ST-Link 有线烧录一次。
   现有固件从 `0x08000000` 开始跑，没有引导程序，无法自己替换自己。
2. **Flash 必须重新分区**，App 的链接地址要从 `0x08000000` 改到 `0x08010000`，
   Keil 的 IROM1 和 `VECT_TAB_OFFSET` 都要改。改完之后**旧固件不能再直接覆盖烧**。
3. **现工程有两个数据没有掉电保存**——密码 `g_password`、卡片列表 `g_card_list`。
   OTA 必然重启，不先补上这两处持久化，**每次升级都会把用户密码重置成 123456、卡片全部清空**。
   这是 OTA 的前置依赖，不是可选项。

## 二、为什么不走别的路

| 方案 | 可行性 | 结论 |
|---|---|---|
| ESP8266 自己 OTA | AT 固件不支持把 STM32 的 bin 写进 STM32 | 否 |
| 让 ESP8266 当 HTTP 客户端拉固件 | 需要 `AT+CIPMUX=1` + 自建文件服务器/公网 HTTPS | 可行但依赖外部服务，作为二期 |
| 蓝牙 OTA | 板载是 BT24 HID 透传模块，不是可编程 BLE SoC | 否 |
| 巴法云 MQTT 分块传输 | 现有链路直接可用，无需任何新服务 | **本期采用** |
| U 盘/SD 卡 | 硬件没有 | 否 |

MQTT 分块的短板是速度（受云端往返和限流影响），但门锁固件只有 38 KB，
按 256 字节一包算约 150 包，实测级别在 **20 秒上下**，完全可以接受。

## 三、Flash 分区

STM32F407ZE 的 512 KB 分为 8 个扇区：S0~S3 各 16 KB、S4 为 64 KB、S5~S7 各 128 KB。
**擦除的最小单位是整个扇区**，所以分区必须按扇区边界切。

| 区域 | 扇区 | 起始地址 | 大小 | 用途 |
|---|---|---|---|---|
| Bootloader | S0–S2 | `0x08000000` | 48 KB | 上电决策、搬运镜像、回滚；OTA 永不擦写 |
| 元数据区 | S3 | `0x0800C000` | 16 KB | 追加式记录：当前状态、版本、CRC、启动次数 |
| **运行区** | S4–S5 | `0x08010000` | 192 KB | App 实际执行的位置（链接地址） |
| **下载区** | S6 | `0x08040000` | 128 KB | OTA 期间新镜像先落这里 |
| **备份区** | S7 | `0x08060000` | 128 KB | 旧镜像的最后一版，回滚用 |

```
0x08000000 ┌──────────────┐
           │  Bootloader  │ 48 KB   S0-S2
0x0800C000 ├──────────────┤
           │  OTA 元数据  │ 16 KB   S3（日志式追加，几乎不擦除）
0x08010000 ├──────────────┤
           │              │
           │   运行区     │ 192 KB  S4-S5  ← App 链接在这里
           │  (App 执行)  │
0x08040000 ├──────────────┤
           │   下载区     │ 128 KB  S6     ← OTA 写入这里
0x08060000 ├──────────────┤
           │   备份区     │ 128 KB  S7     ← 回滚用
0x08080000 └──────────────┘
```

**镜像上限 = 128 KB**（受下载区大小限制）。当前 38 KB，余量 3.4 倍。
打包工具会在超过 128 KB 时直接拒绝。

## 四、为什么是"搬运"而不是 A/B 双镜像

直觉做法是 A/B 两个槽轮流启动。但在这个工程里**行不通**：

> Keil 编译出的固件是**绝对地址**的。链接在 `0x08010000` 的 bin，放到 `0x08040000` 执行，
> 所有函数指针、常量地址、中断向量全是错的，上电必跑飞。

要做真 A/B，有两条路：

- 每次发版编译**两份**（A 版链接 0x08010000、B 版链接 0x08040000），升级时按目标槽推对应的包。
  可行，但每次发版都要出两个 bin，且两份必须版本一致，人工容易搞错。
- 用位置无关代码（PIC）——Keil/ARMCC 在本工程规模下不现实。

所以本方案用更稳的 **"单镜像 + 下载区 + 备份区"**：

```
升级时：新镜像 → 下载区（App 自己写，不动运行区，断电无影响）
重启时：Bootloader 校验下载区 → 把旧镜像拷到备份区 → 擦运行区 → 把新镜像拷进运行区 → 启动
失败时：启动计数超限 → 从备份区把旧镜像拷回运行区
```

代价是每次升级多两次 128 KB 以内的扇区擦除和两次 38 KB 拷贝（约 0.5~1 秒），
换来的是**只需要维护一套链接配置、一个 bin**，出错概率低得多。

## 五、三个角色

### 5.1 Bootloader（48 KB，上电第一段代码）

只做四件事，不联网、不驱动外设：

1. 读元数据区最后一条有效记录；
2. 按状态决定：直接启动 / 校验下载区 / 搬运镜像 / 回滚 / 停在恢复模式；
3. 校验新镜像：长度、CRC32、向量表合法性（栈顶在 `0x20000000~0x20020000`，复位向量在运行区内）；
4. 跳转前清中断、关 SysTick、设 `SCB->VTOR`、设 MSP。

跳转代码（可直接用）：

```c
static void jump_to_app(uint32_t base)
{
    uint32_t sp = *(volatile uint32_t *)base;
    uint32_t pc = *(volatile uint32_t *)(base + 4);

    /* 栈顶必须落在 SRAM；复位向量必须落在运行区内，否则判为坏镜像 */
    if ((sp & 0xFFF00000u) != 0x20000000u) return;
    if ((pc & 0xFFF00000u) != (base & 0xFFF00000u)) return;

    __disable_irq();
    SysTick->CTRL = 0; SysTick->LOAD = 0; SysTick->VAL = 0;
    for (uint32_t i = 0; i < 8; i++) {
        NVIC->ICER[i] = 0xFFFFFFFFu;    /* 关所有中断 */
        NVIC->ICPR[i] = 0xFFFFFFFFu;    /* 清所有挂起 */
    }
    SCB->VTOR = base;
    __set_MSP(sp);
    __enable_irq();
    ((void (*)(void))pc)();
}
```

### 5.2 App 侧 OTA 模块（`HARDWARE/ota/ota.c`）

- 收二进制帧 → 按 offset 写下载区 → 定期回 ack；
- 结束时算整包 CRC32、校验镜像头；
- 写一条"待安装"元数据记录；
- 重启交给 Bootloader。

**不需要新任务**：写一包 256 字节 = 64 个字 = 约 1 ms，直接在网络任务里做，不阻塞 MQTT 心跳。

### 5.3 上位机工具（`tools/`）

- `ota_pack.py`：bin → `.ota`（加 20 字节头，算 CRC32，检查大小），已随本方案提供；
- `ota_push.py`：按下面的协议分块推送、收 ack、断点续传（实现固件后一起补）。

## 六、升级协议

### 6.1 为什么不新开主题

巴法云**每个主题一把私钥**，新开一个 `lock000ota` 主题就要多维护一套密钥，还得让设备同时持有两把。
所以复用现有主题，用**首字节区分**：

- 文本命令：首字节是 ASCII（`u`、`s`、`f`…）；
- 二进制帧：首字节固定 `0x02`。

在 `bemfa_mqtt.c` 的 `on_message()` 里，把"复制成字符串再交给 remote_cmd"之前加一个判断即可，
文本协议完全不受影响。

### 6.2 帧格式（上位机 → 设备，发布到 `lock000/set`）

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | `0x02` | 帧标记 |
| 1 | 1 | type | 1=START 2=DATA 3=END 4=ABORT 5=QUERY |
| 2 | 4 | token | 鉴权令牌，见第八节 |
| 6 | 2 | version | 版本号，如 `0x0102` = v1.2 |
| 8 | 4 | offset | DATA：本包在镜像内的偏移；START：续传起点 |
| 12 | 4 | size | 镜像总长度 |
| 16 | 4 | crc32 | 整包 CRC32 |
| 20 | 2 | len | 本帧数据长度（仅 DATA 用） |
| 22 | n | payload | 固件数据，最多 256 字节 |

固定头 22 字节 + 256 字节数据 = 278 字节，
加主题（11 字节）和 MQTT 固定头（4 字节）约 **293 字节/包**，
所以要把 `MQTT_MAX_PACKET` 从 256 提到 **384**（`s_txbuf` 和解析器缓冲各 +128 字节，RAM 无压力）。

> 256 字节的包在 115200 波特率下占用 UART 约 22 ms，现有 512 字节环形缓冲够用一倍余量，
> 不需要动 `UART3_RX_RING_SIZE`。

### 6.3 设备应答（文本，沿用现有 `remote_cmd_send`）

| 应答 | 含义 |
|---|---|
| `ota=erasing` | 正在擦下载区（1~2 秒，此时不要发数据） |
| `ota=ready,off=<n>` | 就绪，从 offset n 开始发 |
| `ota=ack,off=<n>` | 已收到 n 字节，下一包期望的偏移 |
| `ota=done,ver=<n>` | 校验通过，即将重启 |
| `ota=err,code=<n>[,off=<n>]` | 失败，code 见下 |

| code | 含义 | 处理 |
|---|---|---|
| 1 | 忙（有其他功能在跑） | 等 3 秒重试 |
| 2 | 镜像超过 128 KB | 检查链接配置 |
| 3 | 帧格式/长度非法 | 检查打包工具 |
| 4 | 没有会话（未 START） | 重新 START |
| 5 | offset 跳号 | 从 `err` 里带的 off 续传 |
| 6 | Flash 写失败 | 检查供电，重试 |
| 7 | CRC32 不符 | 重新传 |
| 8 | 镜像头/向量表非法 | 检查是不是把 bootloader 或 hex 当 bin 传了 |
| 9 | 令牌错误 | 检查 `ota_key.h` |
| 10 | 门锁处于开锁状态 | 先关门再升级 |

### 6.4 一次完整升级的时序

```
上位机                          设备
  │  START(ver,size,crc,token)   │
  │─────────────────────────────►│  校验 token / 尺寸 / 门锁状态
  │                              │  擦除下载区（1~2s）
  │        ota=erasing           │
  │◄─────────────────────────────│
  │        ota=ready,off=0       │
  │◄─────────────────────────────│
  │  DATA(off=0,len=256)         │
  │─────────────────────────────►│  写入下载区
  │  DATA(off=256) ... 共 4 包    │
  │─────────────────────────────►│
  │        ota=ack,off=1024      │
  │◄─────────────────────────────│
  │           …… 循环 ……          │
  │  END(size,crc)               │
  │─────────────────────────────►│  CRC32 校验 + 向量表校验
  │                              │  写元数据：待安装
  │        ota=done,ver=258      │
  │◄─────────────────────────────│
  │                              │  500ms 后 NVIC_SystemReset()
  │                              │
  │                        Bootloader：校验下载区 → 备份旧镜像
  │                                    → 擦运行区 → 搬运新镜像 → 跳转
  │                              │
  │                        App：初始化通过、运行 10 秒
  │                              │  → 元数据写 CONFIRMED（本次升级成功）
```

## 七、断电与回滚

这是 OTA 唯一真正重要的部分。四个环节各自的保护：

| 环节 | 断电后果 | 保护手段 |
|---|---|---|
| 擦下载区 / 写下载区 | 下载区残缺 | 运行区没动过，正常启动旧固件；下次 START 重新擦 |
| 校验/写元数据 | 元数据可能写坏 | 日志式**追加**写，坏记录被跳过，上一条仍然有效 |
| Bootloader 搬运中 | 运行区半新半旧 | 元数据先写 `INSTALLING`；上电看到它就重试搬运；下载区校验不过则用备份区恢复 |
| 新固件启动即崩 | 无法确认 | 启动计数 +2 次未确认 → 自动从备份区恢复旧镜像 |

元数据记录（32 字节，追加写入，扇区写满才整体擦除一次）：

| 偏移 | 字段 | 说明 |
|---|---|---|
| 0 | magic `0x4F544131` | "OTA1" |
| 4 | seq | 递增序号，取最大者为当前状态 |
| 8 | state | 0=空闲 1=下载中 2=待安装 3=搬运中 4=待确认 5=已确认 |
| 9 | flags | bit0 运行区有效 / bit1 下载区有效 / bit2 备份区有效 |
| 10 | attempts | 新镜像已尝试启动次数 |
| 12 | version | 版本号 |
| 16 | size / crc32 | 镜像长度与校验值 |
| 28 | crc16 | 前 28 字节校验 |

16 KB ÷ 32 B ≈ **500 条记录**，正常使用十年也写不满；写满时擦一次并立即补写当前状态。

## 八、安全：这一节不能省

现在这条链路上，**任何知道主题名的人都能发 `unlock` 开门**，OTA 更危险——能改固件等于能永久控制设备。
所以：

1. **令牌**：START 帧带 32 位 token = `CRC32(OTA_KEY ‖ size ‖ crc32)`。
   `OTA_KEY` 放在 `HARDWARE/ota/ota_key.h`，**加入 `.gitignore`**，仓库里只留 `ota_key.example.h`。
   设备端做常数时间比较，失败回 `code=9`。
2. **只在关门状态下允许升级**，且升级期间占住功能互斥锁。
3. **升级完成后强制重新确认**：新固件必须走到 CONFIRMED 才算数，否则回滚。

**必须诚实说明**：MQTT 是明文 9501 端口，令牌只能挡住"知道主题但不知道密钥"的人，
挡不住能在网络上抓包的人。真正的安全需要 TLS（9503，本工程未实现）或对镜像做数字签名。
门锁这种产品最终应该走签名，本方案的令牌只是把门槛从"零"抬到"需要拿到 OTA_KEY"。

## 九、详细操作步骤

### A. 一次性改造（开发者，只做一次）

> 建议在 `feature/ota` 分支上做，改完打 tag `v1.0-bootloader`。
> 固件源码是 **GBK + CRLF**，新增 `.c/.h` 也要保持 GBK，否则 Keil 里中文注释乱码。

**A1. 补两个持久化（前置依赖）**
把 `g_password` 和 `g_card_list` 存进元数据区（或备份寄存器）。
不做这一步，每次 OTA 后密码回 `123456`、卡片全丢。

**A2. 建 Bootloader 工程**
- 新建 Keil 工程 `BOOTLOADER/`，芯片同样选 STM32F407ZE；
- IROM1：`0x08000000`，大小 `0xC000`（48 KB）；
- 只包含：启动文件、`system_stm32f4xx.c`、时钟、`FLASH` 驱动、`ota_meta.c`、`main.c`；
- 不初始化 OLED/指纹/舵机/WiFi，**越简单越不容易变砖**；
- 编译后确认 bin < 48 KB（预期 8 KB 左右）。

**A3. 改 App 的链接地址**
- `Options → Target → IROM1`：Start `0x08010000`，Size `0x30000`；
- `USER/system_stm32f4xx.c` 第 309 行改成带守卫的形式：

```c
#ifndef VECT_TAB_OFFSET
#define VECT_TAB_OFFSET  0x00
#endif
```

- **App 工程**在 `Options → C/C++ → Define` 里加 `VECT_TAB_OFFSET=0x10000`；
  Bootloader 工程不加（保持 0x00）。
  这一步不能省：`SystemInit()` 在 `main()` 之前就会把 `SCB->VTOR` 写成
  `FLASH_BASE | VECT_TAB_OFFSET`，如果 App 没定义，它会把 Bootloader 刚设好的
  向量表地址又改回 `0x08000000`，中断全部跳到 Bootloader 的中断向量，表现为"能启动但一进中断就跑飞"。
- 重新编译，`OBJ/demo.hex` 的起始地址应该变成 `0x08010000`。
- Keil 生成 bin 时用 `fromelf --bin --output OBJ\app.bin OBJ\demo.axf`。

**A4. 加分区与元数据模块** `HARDWARE/ota/ota_layout.h`

```c
#define OTA_BL_ADDR      0x08000000u   /* S0-S2, 48KB */
#define OTA_META_ADDR    0x0800C000u   /* S3, 16KB */
#define OTA_META_SECTOR  FLASH_Sector_3
#define OTA_RUN_ADDR     0x08010000u   /* S4-S5, 192KB */
#define OTA_RUN_SECTOR_A FLASH_Sector_4
#define OTA_RUN_SECTOR_B FLASH_Sector_5
#define OTA_DL_ADDR      0x08040000u   /* S6, 128KB */
#define OTA_DL_SECTOR    FLASH_Sector_6
#define OTA_BAK_ADDR     0x08060000u   /* S7, 128KB */
#define OTA_BAK_SECTOR   FLASH_Sector_7
#define OTA_IMAGE_MAX    0x20000u      /* 128KB */
```

**A5. 写 OTA 模块**（`HARDWARE/ota/ota.c`）
- `ota_start()`：校验 token、尺寸、门锁状态 → 擦下载区 → 回 `ready`；
- `ota_data()`：offset 连续性检查 → 写 1 KB RAM 缓冲 → 满则 `FLASH_ProgramWord` 落盘；
- `ota_end()`：补齐 0xFF → 全量 CRC32（读回校验）→ 校验向量表 → 写元数据 → 回 `done` → 复位；
- `ota_abort()`：清会话，不动任何 Flash。

CRC32 用软件实现，和 Python `zlib.crc32` 结果一致：

```c
uint32_t ota_crc32(const uint8_t *p, uint32_t n, uint32_t crc)
{
    crc = ~crc;
    while (n--) {
        crc ^= *p++;
        for (int i = 0; i < 8; i++)
            crc = (crc >> 1) ^ (0xEDB88320u & (uint32_t)(-(int32_t)(crc & 1)));
    }
    return ~crc;
}
```

**A6. 在网络层分流**
`bemfa_mqtt.c` 的 `on_message()`，PUBLISH 分支里：

```c
if (pl[0] == 0x02) {
    ota_handle_frame(pl, pll);   /* 二进制帧，不进文本解析 */
    return;
}
```

同时把 `MQTT_MAX_PACKET` 从 256 改为 384。

**A7. 加查询命令**
`remote_cmd.c` 里加 `ota_info`（回 `ota=info,ver=,slot=,state=`）和 `ota_abort`，
并让 `help=` 列表带上它们。

**A8. 上位机工具**
- `tools/ota_pack.py`：本方案已提供，见第十节；
- `tools/ota_push.py`：实现第六节协议（可复用 `sim/mocklock/mqtt.py` 的编解码）。

**A9. 有线迁移（必须有线，仅此一次）**
1. ST-Link 连板子，先烧 **Bootloader**（`0x08000000`）；
2. 再烧 **App**（`0x08010000`）；
3. 断电重启，确认 OLED 正常、小程序能连上。
> 顺序不能反。先烧 App 到新地址而 Bootloader 还没烧，设备会停在 `0x08000000` 的空白区，表现为"上电没反应"。

**A10. 回归测试**
- 正常升级一次，确认版本号变化、指纹与卡片都还在；
- 传输中途拔电，重新上电应启动旧固件；
- 故意推一个 CRC 错误的包，应回 `code=7`，设备不动；
- 推一个超过 128 KB 的包，应回 `code=2`；
- 新固件里故意 `while(1)`，连续两次未确认后应自动回滚。

### B. 每次发版升级（日常，6 步）

**B1. 改版本号**
`USER/include.h` 加 `#define FW_VERSION 0x0103`（v1.3），编译时带上。

**B2. 生成 bin**
Keil 的 `Options → User → After Build` 加一条：

```
fromelf --bin --output ".\OBJ\app.bin" ".\OBJ\demo.axf"
```

或者命令行：

```bat
fromelf --bin --output OBJ\app.bin OBJ\demo.axf
```

> 一定要用 **bin**，不要用 hex。hex 带地址记录，直接当镜像传会解析失败。

**B3. 打包**

```bat
python tools\ota_pack.py OBJ\app.bin -v 1.3 -o OBJ\app_v1.3.ota
```

输出示例：

```
镜像      OBJ/app.bin
大小      38,660 字节 (37.8 KB)
版本      v1.3 (0x0103)
CRC32     0x8F3A21C4
上限      131,072 字节，余量 92,412 字节
输出      OBJ/app_v1.3.ota (38,680 字节)
```

**B4. 设备就绪**
门锁保持上电、关门状态、小程序显示"在线"。升级过程中不要开门（会回 `code=10`）。

**B5. 推送**

```bat
python tools\ota_push.py --topic lock000 --uid <设备私钥> --file OBJ\app_v1.3.ota
```

工具会打印：

```
START  ota=ready,off=0
  256/38660   ota=ack,off=1024
  1024/38660  ...
  38660/38660 ota=done,ver=259
设备将在 1 秒内重启
```

**B6. 确认**
重启后 10 秒，设备会往主题发 `ota=confirmed,ver=259`；
小程序设置页显示新版本号即升级成功。
如果没有收到 `confirmed`，设备会在第 2 次启动失败后自动回滚，版本号回到上一版。

### C. 失败对照

| 现象 | 原因 | 处理 |
|---|---|---|
| 一直 `ota=err,code=1` | 正在录指纹/刷卡/密码输入 | 等操作结束，或按 `#` 退出 |
| `code=4` | 上位机没发 START 就发 DATA | 检查工具 |
| `code=5,off=xxxx` | 丢包 | 工具应自动从该偏移续传 |
| `code=7` | 传输中被改写/截断 | 重传一次；反复失败查 WiFi 信号 |
| `code=8` | 传的不是 App 的 bin | 检查是不是烧错工程/没改链接地址 |
| `code=9` | OTA_KEY 不一致 | 两端同一份 `ota_key.h` |
| `code=10` | 门锁是开锁状态 | 先 `close` 再升级 |
| 重启后没反应 | Bootloader 没烧 / 链接地址没改 | 用 ST-Link 读 `0x08000000` 确认 |
| 版本号没变 | 新固件未确认，已回滚 | 看串口日志里 Bootloader 的打印 |

## 十、打包工具用法

`tools/ota_pack.py`（纯标准库，Python 3.8+）：

```bat
python tools\ota_pack.py <app.bin> -v <版本> [-o 输出.ota] [--verify]
```

`.ota` 文件格式（20 字节头 + 原始 bin）：

| 偏移 | 长度 | 字段 |
|---|---|---|
| 0 | 4 | magic `SLFW` |
| 4 | 2 | 版本号（大端，0x0103 = v1.3） |
| 6 | 2 | 标志位（保留） |
| 8 | 4 | 镜像长度 |
| 12 | 4 | 镜像 CRC32 |
| 16 | 2 | 头 CRC16-CCITT |
| 18 | 2 | 保留 `0xFFFF` |

`--verify` 会重新读出来校验一遍，推送前建议跑一次。

## 十一、工作量与分期

| 阶段 | 内容 | 规模 | 能否离线验证 |
|---|---|---|---|
| P0 | 密码/卡片持久化（前置） | 约 150 行 | 可在 sim 里跑 |
| P1 | Bootloader + 分区 + 元数据 | 约 400 行 | 只能语法自检 |
| P2 | App 侧 OTA 模块 + 协议 | 约 500 行 | 语法自检 + PC 单测 CRC |
| P3 | 上位机 pack/push 工具 | 约 350 行 | **可以完整跑通** |
| P4 | 小程序升级页（进度条、版本显示） | 约 300 行 | 渲染截图可验证 |
| P5 | 二期：HTTP 直拉（局域网/公网） | 约 400 行 | 需服务器 |

P1~P3 是"能用"的最小闭环。P5 的收益是速度（38 KB 走 HTTP 约 1 秒）和不依赖云端限流，
但需要一台能放固件的服务器，且 ESP8266 要开多连接，改动面更大。

## 十二、必须说清楚的三个风险

1. **本机没有 Keil，也没有板子。**
   方案里的固件代码只能做 `gcc -fsyntax-only` 语法自检，**不能真实编译，更不能验证烧录后的行为**。
   Bootloader 这类代码一旦有地址错误就是砖，最终必须在 Keil 里 Rebuild 并用 ST-Link 实测。
2. **第一次迁移必须拆机接线。**
   OTA 只能解决"以后不用再拆"，解决不了"第一次怎么进去"。这是所有 MCU OTA 的共同前提。
3. **巴法云的限流未知。**
   256 字节/包、每秒几条，没有官方明确数值。若实测被限流，把窗口从 4 降到 2，
   或改用二期 HTTP 方案。文档里的 20 秒是估算，不是实测值。
